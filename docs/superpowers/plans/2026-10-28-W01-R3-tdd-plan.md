## RED phase — prove the gap exists

### T01: Competing fund operations (same reference, different rewards)

- **File**: `src/__tests__/reward-atomic-reference.test.ts` (NEW)
- **Setup**: Two draft rewards (rewardA, rewardB), independent admin
- **Action**: `fundReward(rewardA, admin, { type: 'admin_grant', reference: 'ref_X' }, key1)`
  then `fundReward(rewardB, admin, { type: 'admin_grant', reference: 'ref_X' }, key2)`
- **Expected RED**: Second call throws DUPLICATE_REFERENCE (409) — but currently the outer
  `checkReferenceNotReused()` catches this sequentially. This test is GREEN on current main.
- **Why still needed**: Proves the application-level check works sequentially. T06 proves the
  DB-level gap.
- **Maps to**: Acceptance criteria 1

### T02: DB-level uniqueness — direct INSERT bypass

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Setup**: Fund rewardA with reference 'ref_X' via `fundReward()`
- **Action**: Direct `db.prepare('INSERT INTO reward_transactions ...').run(...)` with same
  `funding_reference = 'ref_X'` and `transaction_type = 'fund'`
- **Expected RED**: INSERT succeeds (no DB constraint prevents it)
- **Expected GREEN**: INSERT fails with UNIQUE constraint violation
- **Maps to**: Acceptance criteria 6

### T03: Same-operation retry (idempotent)

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Setup**: Fund rewardA with key=K1, reference='ref_X'
- **Action**: Call fundReward again with same key=K1, reference='ref_X'
- **Expected**: Returns same reward, no second transaction created
- **Maps to**: Acceptance criteria 2

### T04: Rollback does not consume reference

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Setup**: Fund rewardA (succeeds, status=funded)
- **Action**: Try to fund rewardA again with a new key — this will fail because reward is
  already funded (assertTransition fails). Verify no transaction was created.
  Then verify a different reward CAN use the same reference if the first didn't actually use it.
- **Realistic rollback test**: Create a scenario where the transaction rolls back (e.g. by
  mocking writeLedgerEntry to throw mid-transaction), verify reference is not consumed.
- **Maps to**: Acceptance criteria 4

### T05: Cancel/expire do not release reference

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Setup**: Fund rewardA with ref_X, then cancel rewardA
- **Action**: Try to fund rewardB with same ref_X
- **Expected**: DUPLICATE_REFERENCE (409) — cancelled reward's reference remains consumed
- **Maps to**: Acceptance criteria 5

### T06: TOCTOU simulation — application check bypassed, DB catches it

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Setup**: Fund rewardA with ref_X (succeeds)
- **Action**: Manually INSERT a fund transaction for rewardB with ref_X, bypassing
  `checkReferenceNotReused()` (simulating the TOCTOU race)
- **Expected RED**: INSERT succeeds (the DB has no protection)
- **Expected GREEN**: INSERT fails (UNIQUE index catches it)
- **Maps to**: Acceptance criteria 1, 6

### T07: NULL references are unconstrained

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Setup**: Two draft rewards, independent admin
- **Action**: Fund both with `{ type: 'admin_grant' }` (no reference — NULL)
- **Expected**: Both succeed — NULLs are distinct in UNIQUE constraints
- **Maps to**: Acceptance criteria 11

### T08: Empty/whitespace references normalized to NULL

- **File**: `src/__tests__/reward-atomic-reference.test.ts`
- **Action**: Fund with `{ type: 'admin_grant', reference: '' }` and
  `{ type: 'admin_grant', reference: '   ' }`
- **Expected**: Both treated as NULL (no reference stored), both succeed
- **Verify**: `funding_reference` in reward_transactions is NULL, not empty string
- **Maps to**: Acceptance criteria 12

### T09: Error message does not leak reward ID (A2)
