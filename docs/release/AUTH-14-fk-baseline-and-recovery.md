# AUTH-14: FK baseline and release recovery

This candidate preserves pre-existing SQLite foreign-key violations during the W03 reward transaction migration only when an operator supplies an independently reviewed count and exact SHA-256 baseline. Without a baseline, any violation remains a refusal. A supplied baseline is evidence, not authorization to modify a database.

The migration checks the baseline before taking the write lock, again inside an immediate transaction before reconstruction, and after reconstruction before committing. Schema and dependent-object identity are also rechecked inside that transaction. A mismatch, unsafe integer, malformed hash, integrity failure, or unsupported schema refuses the migration. A successful explicit-baseline migration records the count and digest in `migration_002_reward_txn_check_fk_baseline` alongside the existing receipt. It never deletes or repairs the orphan.

On an isolated protected copy, `--plan DATABASE_PATH` displays the observed FK count and digest. After independent review of the precise database identity and baseline, the explicit CLI form is `--apply DATABASE_PATH --fk-count COUNT --fk-sha256 HASH`. The values must be recaptured and reviewed for the actual quiesced production database; rehearsal hashes are not deployment approval. The digest matches `release_preflight.database_metadata` and is not a substitute for examining the underlying private evidence. SQLite reports the child table, rowid, parent table, and FK index: the digest does not capture every orphan-row value or the missing parent key. Compare the complete protected row and dependent data separately during rehearsal and final verification.

The deployment recovery boundary covers the controlled stop and every subsequent preparation step. Recovery still requires the existing image, checkout, database, policy, and financial-state gates. If those gates reject restoration, services are contained where possible; failure to verify containment is reported separately. This does not protect against host or process failure during a stop, nor guarantee that old images remain compatible after new application writes.

Before a production decision, complete independent review, CI, exact-image and protected-copy rehearsals, writer admission planning, backup/restore verification, policy review, and a migration-window procedure. Never use a copied SQLite main file as a live WAL backup.
