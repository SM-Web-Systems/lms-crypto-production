## Problems and resulting behavior

Legacy `lesson_completions.completed_at` can remain `NOT NULL` after the previous additive progress-column migration. The API writes an explicit NULL timestamp for in-progress playback, so an upgraded legacy installation can reject that write despite normal startup succeeding. The previous tests repeated a local copy of the additive migration rather than invoking production code.

Startup previously warned about every foreign-key violation both before and after migrations. Because startup intentionally disables FK enforcement around its schema transaction, a migration could introduce an orphan and still commit. A count or SQLite table/rowid/foreign-key tuple alone also cannot identify changed referenced values on an existing orphan.

The actual startup helper now reconstructs a legacy completion table transactionally, changing only the target column's NOT NULL constraint in its original DDL. Startup captures private exact FK evidence during read-only preflight, rechecks it under `BEGIN IMMEDIATE` before writes, and rejects new or changed evidence before committing migrations. Existing exact orphan evidence remains grandfathered, matching previous preflight acceptance; it is not declared valid or repaired. The existing `submissions.graded_by` schema-signature exception and all other schema/key checks remain unchanged.

## Completion evidence and reconstruction contract

Completion is represented by `completed_at IS NOT NULL` in this application. No `completed` boolean, default false value or new timestamp is introduced. Existing timestamps, marking users, IDs, physical rowids, progress and playback positions remain unchanged. Missing progress/position columns are added nullable; an unknown historical progress percentage is not fabricated as 100. New in-progress writes must explicitly supply `completed_at = NULL`, as the existing API already does. Existing completed rows continue to count as completed regardless of nullable progress metadata.

The helper requires the caller-owned transaction and FK enforcement temporarily disabled before any schema change. It uses SQLite's documented create/copy/drop/rename procedure, never renaming the original table. Its small lexer distinguishes identifiers, keywords, literals, punctuation and comments so changing NOT NULL does not rewrite a default string or a different column. Before copying or dropping rows, an independent metadata invariant requires identical `table_xinfo` metadata except `completed_at.notnull` changing from 1 to 0, and an identical FK list. Original extra columns/defaults/checks, primary/unique/FK constraints, rowids, attached indexes/triggers and external views/inbound FKs are retained. Generated columns, if present, are recomputed by SQLite from the retained DDL rather than directly inserted. `legacy_alter_table` is temporarily enabled during replacement to preserve external references and restored immediately.

Bespoke CHECK constraints referencing `completed_at`, an ambiguous/unsupported DDL shape, rowid-shadowing columns, AUTOINCREMENT or WITHOUT ROWID completion tables requiring reconstruction, or a leftover `_lesson_completions_nullable` object refuse the migration. AUTOINCREMENT owns historical allocation state in `sqlite_sequence`; this implementation refuses that layout instead of lowering its high-water mark. Layout keywords are recognized as actual lexer tokens at their grammatical depth, so harmless default/comment phrases do not trigger refusal. No stale object is deleted to force progress. The whole startup transaction rolls back, including earlier additive changes. Such layouts need an independently reviewed migration; do not weaken their checks or rewrite existing evidence to silence a refusal. Preserved custom triggers can still impose bespoke NULL policies: the known legacy NOT NULL repair is not proof that every unknown custom layout accepts pending writes, and owner rehearsal must inspect those semantics.

This follows the [SQLite table reconstruction procedure](https://www.sqlite.org/lang_altertable.html) and its [foreign-key/ALTER TABLE behavior](https://www.sqlite.org/foreignkeys.html). The actual bundled SQLite behavior is covered with synthetic dependencies and real-process restarts, not inferred from documentation alone.

## Foreign-key contract

Each private evidence digest binds the child table, exact integer rowid, parent table, FK slot and definition, child primary key and referenced child values. Big integer, binary and REAL values retain distinct typed encodings, including positive/negative infinity rather than JSON-null collisions. Changes to an orphan's referenced value or primary identity therefore fail even when the number and raw PRAGMA tuples are identical. Unrelated metadata/additive columns may change without misclassifying an unchanged orphan. Resolving an existing orphan removes evidence and is allowed; no migration repair is performed by this implementation.

The initial read-only inspection is one SQLite read transaction. After opening the writable connection, `BEGIN IMMEDIATE` prevents concurrent writers while a second snapshot is compared to preflight evidence and migrations execute. The final snapshot must be a subset of the stable pre-migration evidence. Newly introduced or changed evidence throws inside the transaction, so earlier migrations and the offending writes roll back. Runtime FK enforcement is explicitly enabled and checked before/after the migration window. The application connection closes on refusal.

Warnings contain aggregate counts only. They do not print rowids, primary keys, referenced values or table names. A WITHOUT ROWID table with existing FK violations has no unambiguous row locator in `PRAGMA foreign_key_check`; the current implementation refuses that unsupported evidence before writing rather than hashing an ambiguous identity. Other custom layouts still require owner rehearsal. Evidence is an observation within this startup, not a durable allowlist, a cryptographic approval or proof that an external historical write was legitimate.
